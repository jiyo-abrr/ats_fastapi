# Applications domain — plan

## Goal

Add the `applications` domain: applicants apply to a `JobPost`, HR/admin review and move applications through a status lifecycle. This is the domain `job_post_exclusions` was built to feed — right now nothing enforces "don't let applicants of job post A apply to job post B"; this plan is what finally reads that data and enforces it.

## Data model

New domain `app/domains/applications/`, one table: `applications`.

| column | type | notes |
|---|---|---|
| `id` | UUID PK | `uuid.uuid4()`, generated in the service like every other domain |
| `job_post_id` | UUID FK → `job_posts.id`, `ondelete=CASCADE` | owned by the job post — deleting a job post deletes its applications, same asymmetric-cascade rule as `job_post_tags`/`job_post_exclusions` |
| `applicant_id` | UUID FK → `users.id` | no cascade — there's no user-delete endpoint yet, so this is moot for now; default RESTRICT is fine |
| `status` | `String(20)` + `CheckConstraint`, default `submitted` | `StrEnum` in `enums.py`, same pattern as `JobPostStatus` — `submitted`, `under_review`, `accepted`, `rejected`, `withdrawn` |
| `resume_object_key` | `String`, not nullable | **snapshot**, not a live reference — see "Resume snapshotting" below |
| `created_at` / `updated_at` | timestamp, server default | standard |

**Uniqueness**: a partial unique index on `(job_post_id, applicant_id) WHERE status != 'withdrawn'` — one *active* application per applicant per job post. `withdrawn` is the only status that frees up the slot; **`rejected` is terminal and still blocks re-applying** (confirmed) — a rejected applicant cannot try again for the same job post. Enforced at the DB level (hand-edit the autogenerated migration to add `postgresql_where=text("status != 'withdrawn'")`), not just in the service — matches how the codebase already treats data integrity as the DB's job wherever a constraint can express it (see `ck_job_post_exclusion_not_self`).

## Business rules

1. **Only applicants apply.** `role != "applicant"` → new `OnlyApplicantsCanApplyError(ForbiddenError)`. HR/admin creating an "application" isn't a real scenario in this system.
2. **Job post must be open.** `job_post.status != "published"` → `JobPostNotAcceptingApplicationsError(ValidationError)` (400 — the request itself is invalid given current state, not a conflict with existing data).
3. **No duplicate active application.** Caught by the partial unique index; service catches the resulting `IntegrityError` → `uow.rollback()` → `DuplicateApplicationError(ConflictError)` (409) — identical pattern to `PositionInUseError`/`TagInUseError`.
4. **Exclusion enforcement — the actual point of this domain.** Before creating the application for `job_post_id=X`, fetch `X.excluded_job_post_ids`. For each excluded id `Y`, check whether the applicant has *any* application (any status, including withdrawn — once you've touched the excluded job, you're still excluded) against `Y`. If so → `ApplicantExcludedError(ForbiddenError)` (403 — this is a policy ban, not a data conflict or bad input). **Confirmed: the error message names the conflicting job post by its title** (e.g. `"You cannot apply to this job post because you previously applied to 'Backend Engineer'"`) — the service resolves `Y`'s `job_title` via `JobPostRepository.get_by_id` before raising, so the exception carries a human-readable message, not just an id.
5. **Ownership gates access, not a permission.** An applicant can only see/withdraw their *own* applications — enforced by comparing `current_user.id == application.applicant_id` in the service (raises `ApplicationNotFoundError` on mismatch, not `ForbiddenError` — don't leak existence of another applicant's application via a 403 vs 404 distinction). This mirrors how `manage_own_profile` is conceptually scoped elsewhere: no new permission needed for "manage my own applications."
6. **HR/admin review is gated by a new permission**, `manage_applications` — seeded, granted to `admin`+`hr` by default (same shape as `manage_jobs`/`manage_hr_accounts`). **Confirmed flat**: any HR/admin with this permission can view/decide on every application, for every job post — no per-HR-user ownership scoping (that would require adding a `created_by` concept to `JobPost`, which doesn't exist and isn't in scope here). One permission covers list-all + status transitions; no need to split "view" from "decide" unless later requested.
7. **Withdraw is applicant-only; status transitions (`under_review`/`accepted`/`rejected`) are HR/admin-only.** An applicant can move `submitted`/`under_review` → `withdrawn`; nothing else. HR/admin cannot set `withdrawn` (that's the applicant's action) and cannot un-withdraw. Invalid transitions → `InvalidApplicationStatusTransitionError(ValidationError)`.

### Resume snapshotting

`User.resume_object_key` can change after an application is submitted (nothing stops re-signup logic evolving later, and conceptually "the resume I applied with" shouldn't silently change if the user's profile resume changes). So `ApplicationService.create()` copies the applicant's *current* `resume_object_key` into the application row at creation time rather than joining back to `User` on every read. This is a deliberate snapshot, not a missed eager-load — worth a comment in the model so a future reader doesn't "fix" it into a relationship.

## File layout (mirrors every existing domain)

```
app/domains/applications/
  models.py        # Application (ORM) — imports JobPost/User models for FKs only, no relationship() needed
                    # beyond what _to_entity requires (see eager-loading note below)
  entities.py       # Application (dataclass) — job_post_id, applicant_id, status,
                    # resume_object_key, created_at, updated_at (no denormalized job_post/user fields —
                    # unlike JobPost's company_address_label; the list endpoints get their inline
                    # job_title/applicant name from a projection query instead, not from this entity —
                    # see Projection queries below)
  enums.py          # ApplicationStatus(StrEnum)
  exceptions.py     # ApplicationNotFoundError, DuplicateApplicationError,
                    # ApplicantExcludedError(ForbiddenError) — carries the conflicting job post's title
                    # in its message, OnlyApplicantsCanApplyError, JobPostNotAcceptingApplicationsError,
                    # InvalidApplicationStatusTransitionError
  repository.py     # ApplicationRepository(BaseRepository[...]) — add get_active_for(job_post_id,
                    # applicant_id) and has_any_application_for(applicant_id, job_post_id) for the
                    # exclusion check, PLUS the two projection queries below (list_for_review,
                    # list_for_applicant); async throughout, per the rest of the codebase
  service.py        # ApplicationService — depends on JobPostRepository (validate job_post state,
                    # resolve the excluded job post's title for ApplicantExcludedError) and
                    # RolePermissionRepository (the owner-or-manage_applications check on
                    # GET /applications/{id}) — one-way dependency, same direction as
                    # job_posts -> positions/tags/company_addresses. No UserRepository needed: the
                    # resume snapshot comes straight off current_user (already fetched by
                    # get_current_user), no second lookup required.
  dependencies.py   # DI factory
  router.py         # see endpoints below
  schemas.py        # ApplicationCreate, ApplicationOut, ApplicationStatusUpdate,
                    # ApplicationReviewOut, ApplicationSummaryOut (see Projection queries below)
```

### Projection queries for the two list endpoints (in scope, not deferred)

Both list endpoints skip full-entity hydration entirely — neither one needs a whole `Application`/`JobPost`/`User` object, so neither goes through `_to_entity`/`repo.map_many`. This means they **don't use the `QueryBuilder`+`apaginate` pattern** the other domains' list endpoints use — `QueryBuilder(Model)` only knows how to build a `select()` against a single ORM class, and these queries join across three tables with a fixed, curated column set. `apaginate` still works here (it accepts any `Select`, not just a `QueryBuilder`-built one) — it's specifically `QueryBuilder`'s dynamic-filter machinery that doesn't apply, so filtering becomes explicit typed query params instead of the generic `?filters={"field":{"$eq":...}}` JSON syntax.

**`GET /applications` (HR/admin review list)** — `ApplicationReviewOut`: `id`, `status`, `created_at`, `job_post_id`, `job_title`, `applicant_id`, `applicant_first_name`, `applicant_last_name`, `applicant_email`.

```python
# applications/repository.py
async def list_for_review(
    self, *, job_post_id: uuid.UUID | None, status: str | None
) -> Select:
    query = (
        select(
            ApplicationModel.id,
            ApplicationModel.status,
            ApplicationModel.created_at,
            ApplicationModel.job_post_id,
            JobPostModel.job_title,
            ApplicationModel.applicant_id,
            UserModel.first_name.label("applicant_first_name"),
            UserModel.last_name.label("applicant_last_name"),
            UserModel.email.label("applicant_email"),
        )
        .join(JobPostModel, JobPostModel.id == ApplicationModel.job_post_id)
        .join(UserModel, UserModel.id == ApplicationModel.applicant_id)
        .order_by(ApplicationModel.created_at.desc())
    )
    if job_post_id is not None:
        query = query.where(ApplicationModel.job_post_id == job_post_id)
    if status is not None:
        query = query.where(ApplicationModel.status == status)
    return query
```

```python
# applications/service.py — thin pass-through, no business logic, just so the
# router depends on the service and never the repository directly
async def list_for_review(self, *, job_post_id, status) -> Select:
    return await self.applications.list_for_review(
        job_post_id=job_post_id, status=status
    )


# applications/router.py
@router.get(
    "", response_model=Page[ApplicationReviewOut], dependencies=[_manage_applications]
)
async def list_applications(
    job_post_id: uuid.UUID | None = None,
    status: ApplicationStatus | None = None,
    db: AsyncSession = Depends(get_db),
    service: ApplicationService = Depends(get_application_service),
) -> Page[ApplicationReviewOut]:
    query = await service.list_for_review(job_post_id=job_post_id, status=status)
    return await apaginate(
        db,
        query,
        transformer=lambda rows: [ApplicationReviewOut.model_validate(r) for r in rows],
    )
```

**`GET /applications/me` (applicant's own list)** — `ApplicationSummaryOut`: `id`, `status`, `created_at`, `job_post_id`, `job_title`. Applicants already know who they are, so no applicant columns needed — just enough to render "your applications" without a second round-trip to `/job-posts/{id}` per row.

```python
# applications/repository.py
async def list_for_applicant(self, applicant_id: uuid.UUID) -> Select:
    return (
        select(
            ApplicationModel.id,
            ApplicationModel.status,
            ApplicationModel.created_at,
            ApplicationModel.job_post_id,
            JobPostModel.job_title,
        )
        .join(JobPostModel, JobPostModel.id == ApplicationModel.job_post_id)
        .where(ApplicationModel.applicant_id == applicant_id)
        .order_by(ApplicationModel.created_at.desc())
    )
```

`GET /applications/{id}` (single-item detail) stays on the full-entity path — `ApplicationOut` from `_to_entity`, no projection — since a detail view is exactly the "I need the whole thing" case eager/full-entity loading is for; it's only the *list* views that wanted a handful of columns from someone else's table.

Both list routes call a thin `ApplicationService.list_for_review()`/`list_for_applicant()` pass-through rather than `ApplicationRepository` directly — the query itself is still built and owned by the repository, this is purely a layering rule: **the router only ever depends on the service, never the repository**, even for the one case (list endpoints) where the service method has no business logic to add. Keeps the "router → service → repository" chain unbroken everywhere, rather than making list endpoints a second kind of exception on top of the query-construction one.

## API endpoints

All under `/api/v1/applications`, all require auth (`get_current_user`):

| method | path | who | notes |
|---|---|---|---|
| POST | `/applications` | applicant only | body: `job_post_id` |
| GET | `/applications/me` | any authenticated applicant | `Page[ApplicationSummaryOut]` — projection query joined to `job_posts`, own applications only |
| GET | `/applications/{id}` | owner or `manage_applications` | `ApplicationOut`, full entity — 404 (not 403) if neither owner nor permitted |
| GET | `/applications` | `manage_applications` | `Page[ApplicationReviewOut]` — projection query joined to `job_posts`+`users`; explicit `job_post_id`/`status` query params (not the generic querybuilder JSON filter — see "Projection queries" above) |
| POST | `/applications/{id}/withdraw` | owner only | `submitted`/`under_review` → `withdrawn` |
| PATCH | `/applications/{id}/status` | `manage_applications` | `under_review`/`accepted`/`rejected` only |

## Testing plan

Unit tests (`tests/unit/applications/test_service.py`, `AsyncMock` repos, matching every other domain):
- rejects non-applicant creating an application
- rejects application to a non-`published` job post
- rejects duplicate active application (simulated `IntegrityError` from the mock)
- **the core case**: applicant already has an application against `Y`, `X` excludes `Y` → `ApplicantExcludedError` whose message contains `Y`'s job title
- applicant with no conflicting history → succeeds, resume snapshot copied from `current_user.resume_object_key`
- owner can withdraw; non-owner gets `ApplicationNotFoundError` (not `ForbiddenError`) attempting to view/withdraw someone else's application
- HR/admin can transition `submitted → under_review → accepted`; rejects `accepted → under_review` (no backwards transitions) and rejects HR/admin trying to set `withdrawn`

No live-DB test for the partial unique index, or for `list_for_review`/`list_for_applicant`'s actual SQL (mocked repos can't exercise a real constraint or a real join) — add both to the "no integration tests yet" gap already noted in `CLAUDE.md`, same caveat as the existing tag/exclusion join-query logic. What *is* unit-testable without a DB: the router-level column mapping (`ApplicationReviewOut.model_validate(row)` on a hand-built fake `Row`-like object/namedtuple) and the query-param → `WHERE` clause wiring at the repository-call level (asserting `list_for_review` was called with the right `job_post_id`/`status` args from the mocked router test).

## Decisions confirmed

- No cover letter field — `Application` carries no free-text applicant input beyond the resume snapshot.
- `rejected` is terminal: it blocks re-applying to the same job post, same as any other active status. Only `withdrawn` frees the slot.
- `ApplicantExcludedError` names the conflicting job post by title.
- `manage_applications` is flat — no per-HR-user ownership scoping.
- Both list endpoints (`GET /applications`, `GET /applications/me`) use purpose-built projection queries with inline `job_title`/applicant name, not full-entity hydration — in scope now, not deferred.
