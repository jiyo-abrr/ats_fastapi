# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`ats-fastapi` is an Applicant Tracking System API built with FastAPI. The app lives under `app/` (`app/main.py` is the FastAPI entrypoint — there is no root-level `main.py`). Currently implemented: JWT-based signup/login authentication, with resumes uploaded to MinIO and profiles stored in Postgres via SQLAlchemy. The app is fully **async SQLAlchemy** end to end (`AsyncSession`, `create_async_engine`) — see "Async architecture" below before touching any repository/service/router.

## Architecture

Domain-based layout, not layered-by-type. Each business domain owns its full vertical slice:

```
app/
  core/
    exceptions.py          # DomainError + 5 HTTP-semantic subclasses (NotFoundError/ConflictError/UnauthorizedError/ForbiddenError/ValidationError) — the ONLY place that knows about HTTP status codes for business errors
    exception_handlers.py  # maps each category above to its status code, once, centrally; plus the catch-all Exception -> 500
    repository.py          # BaseRepository[ModelType, EntityType, IdType] — generic async get_by_id/add/delete/list_all/map_many (query/staging only, no commit), mapping ORM rows <-> domain entities via each subclass's async _to_entity / sync _to_model; IdType lets a domain key on non-UUID PKs (e.g. RevokedRefreshToken keys on a str jti)
    unit_of_work.py        # UnitOfWork — async flush/commit/rollback for the whole request's AsyncSession
    ...                    # config, db engine/session, JWT + password primitives, generic MinIO client
  domains/
    auth/
      models.py            # SQLAlchemy ORM models — persistence only, touched ONLY by this domain's repository
      entities.py           # plain @dataclass domain entities (User, RevokedRefreshToken) — no SQLAlchemy, no FastAPI. What services actually operate on.
      exceptions.py         # EmailAlreadyRegisteredError, InvalidCredentialsError, InvalidRefreshTokenError, InvalidAccessTokenError, UnsupportedResumeTypeError, ResumeTooLargeError
      schemas.py            # Pydantic request/response schemas
      repository.py         # UserRepository(BaseRepository[UserModel, entities.User, uuid.UUID]) — only adds query methods the generic base can't cover (get_by_email)
      service.py            # business logic as a class (AuthService), constructed with its repository + a UnitOfWork; never imports fastapi or sqlalchemy
      dependencies.py       # FastAPI Depends() providers for this domain (get_current_user, get_auth_service, get_user_repository)
      router.py             # thin, version-agnostic — endpoints just call the service; doesn't know it's mounted under /api/v1
    rbac/
      models.py            # Role, Permission, RolePermission (ORM)
      entities.py           # Role, Permission (plain dataclasses)
      exceptions.py         # PermissionDeniedError, RoleNotFoundError, PermissionNotFoundError
      repository.py        # RoleRepository, PermissionRepository, RolePermissionRepository
      service.py            # RBACService — grant/revoke/list, raises the exceptions above
      dependencies.py      # require_permission(key) — the enforcement mechanism every domain gates on
      router.py             # admin-only endpoints to inspect/reconfigure role_permissions live
    positions/             # Position — CRUD only, no cross-domain dependency
    tags/                  # Tag — CRUD only, no cross-domain dependency
    company_addresses/     # CompanyAddress — CRUD only, no cross-domain dependency (lat/long reserved for future geolocation search)
    job_posts/
      models.py            # JobPost, JobPostTag, JobPostExclusion (ORM) — imports Position/CompanyAddress models for relationship()
      entities.py           # JobPost (plain dataclass); imports Tag from tags.entities
      enums.py               # EmploymentType, JobPostStatus (StrEnum — Pydantic validates at the request boundary, no domain exception needed for bad values)
      exceptions.py         # JobPostNotFoundError only — Position/Tag/CompanyAddress each own their own NotFoundError/InUseError
      repository.py         # JobPostRepository — owns the job_post_tags/job_post_exclusions join queries + add_tag/remove_tag/add_exclusion/remove_exclusion
      service.py            # JobPostService — depends on PositionRepository/CompanyAddressRepository/TagRepository from their own domains to validate FKs
      dependencies.py       # DI factory; wires in the other 3 domains' repository dependencies
      router.py             # public GET, manage_jobs-gated write
    applications/          # applicant -> job post candidacy; status pipeline (applied/prescreening/interview/denied/success/failed/disqualified/withdrawn)
      models.py            # Application, AssessmentDeadlineExtension (ORM) — plain FK columns to job_posts/users, no relationship(); a partial unique index enforces one *active* (non-withdrawn) application per applicant per job post
      entities.py           # Application, AssessmentDeadlineExtension (plain dataclasses)
      enums.py               # ApplicationStatus (StrEnum, 8 values)
      exceptions.py         # ApplicationNotFoundError, DuplicateApplicationError, ApplicantExcludedError, OnlyApplicantsCanApplyError, JobPostNotAcceptingApplicationsError, InvalidApplicationStatusTransitionError, InvalidAssessmentDeadlineExtensionError
      repository.py         # ApplicationRepository — also owns list_for_review/list_for_applicant, raw projection Selects (job_posts/users joined in, not full entity hydration) returned to the router for apaginate()
      service.py            # ApplicationService — depends on JobPostRepository (exclusion/status checks) + RolePermissionRepository (owner-or-manage_applications check in get()); never imports the assessments domain (see below)
      dependencies.py, router.py, schemas.py
    assessments/           # grouping namespace only (not a domain itself) — a deliberate one-off exception to the flat-domain convention, since these 4 sub-packages all orbit one feature; see docs/plans/assessments-domain.md
      pre_assessment_templates/  # standalone domain: PreAssessmentTemplate + PreAssessmentQuestion, manage_jobs-gated CRUD (reads gated too — unlike positions/tags/job_posts, these aren't public listings). Questions are fully mutable: `POST /{id}/questions` (append), `PUT /{id}/questions/{qid}` (edit), `DELETE /{id}/questions/{qid}`, `PUT /{id}/questions/reorder` (body `{"question_ids": [...]}` — must be the template's exact current set; rewrites `order_index` 0..n). All 4 return the refreshed template. No guard against editing a question whose template already has attempts — deliberate, keeps these 3 domains independent of `attempts` (HR owns the consequences). A question row is `{order_index, prompt, question_type, config, time_limit_seconds}` — **no per-question `instructions`** (dropped in migration `ffd55849b8a5`; the applicant-facing guidance is the template-level `instructions`, shown once before the attempt).
      culture_fit_templates/     # standalone domain: CultureFitTemplate + CultureFitQuestion, same shape as pre_assessment_templates
      technical_assessment_templates/  # standalone domain: TechnicalAssessmentTemplate + TechnicalAssessmentQuestion, same shape as pre_assessment_templates
      attempts/              # the actual "assessments" domain: AssessmentAttempt/AssessmentAnswer/AssessmentAttemptReopen; dispatches to whichever of the 3 template domains an attempt's template_type names (no DB FK across the boundary — see "Applications and assessments" below)
  api/
    v1.py                  # version-specific aggregator: mounts each domain's router under /api/v1 (e.g. auth_router -> /api/v1/auth/*)
    router.py              # top-level aggregator: api_router combines every active version (currently just v1) into one router
  scripts/
    create_admin.py         # one-off CLI to bootstrap the first admin account (uv run python -m app.scripts.create_admin)
    seed_dummy_data.py      # dev-only: fills the DB with dummy users/positions/tags/addresses/templates/job posts/applications/attempts (uv run python -m app.scripts.seed_dummy_data [--wipe]). Writes ORM models directly (not services) so it can build API-unreachable states (disqualified application, expired attempt). No-op if already seeded; --wipe deletes all non-admin data first. Dummy user password: Password123!. Resumes are key-only — nothing uploaded to MinIO.
  main.py                  # includes app.api.router.api_router (NOT v1_router or domain routers directly)
```

Every `__init__.py` in this project is empty — a plain package marker, nothing else. Actual logic always lives in an explicitly-named module. Don't put logic in `__init__.py`, even for something as small as a router aggregator — it's easy to miss and invites circular-import surprises as the package grows.

When adding a new domain, mirror this structure under `app/domains/<name>/`: `models.py` (ORM) + `entities.py` (plain dataclass) + `exceptions.py` (domain errors) + `repository.py` + `service.py` + `dependencies.py` + `router.py` + `schemas.py` (Pydantic request/response schemas). Route handlers stay plain functions (FastAPI's DI is built around that); business logic goes in a service class per domain, and that service depends on a repository class rather than querying the ORM directly — and only ever sees that domain's `entities`, never its `models`. New domain repositories should subclass `app.core.repository.BaseRepository[Model, Entity, IdType]`, implement `_to_entity`/`_to_model`, and only add query methods the base CRUD doesn't cover — don't re-implement `get_by_id`/`add`/etc. per domain (composite-key join tables are the one exception — see `rbac.RolePermissionRepository` below). Register new domain routers in the relevant `app/api/vN.py`, not directly in `main.py` — domain routers must stay unaware of versioning. Gate any endpoint that isn't universally accessible with `Depends(require_permission("..."))` from `app.domains.rbac.dependencies` — see below.

**Async architecture.** Everything from `get_db()` down is `async`/`await` — routers, services, repositories. Rules that follow from that:
- **Dual engine in `app/core/database.py`.** A sync `engine`/`SessionLocal` (used only by Alembic, which manages its own `engine_from_config` internally and never imports this) sits alongside the async `async_engine`/`AsyncSessionLocal` that `get_db()` yields from. Both point at the same `DATABASE_URL` — `psycopg` (the driver) dispatches sync vs async purely by `create_engine()` vs `create_async_engine()`, no separate driver needed. `AsyncSessionLocal` sets `expire_on_commit=False` so entities built from a row right after `commit()` don't trigger a lazy-refresh.
- **No `.query()`.** `AsyncSession` doesn't support the legacy Query API — every custom lookup is `await self.db.execute(select(Model).where(...))` then `.scalar_one_or_none()` / `.scalars().all()`.
- **Relationship access requires eager loading, always.** Under `AsyncSession` there is no implicit lazy-load — touching an unloaded relationship attribute (e.g. `obj.role.name`, `obj.company_address.label`) raises `MissingGreenlet`. Any repository whose `_to_entity` touches a relationship overrides `get_by_id`/`list_all` to add `.options(selectinload(Model.relationship))` — see `auth.UserRepository` (loads `.role`) and `job_posts.JobPostRepository` (loads `.company_address` + `.position`, via the shared `_EAGER_OPTIONS` tuple). Any new query path against those models (including ad-hoc `QueryBuilder` queries — see below) needs the same `.options(...)` applied before execution.
- **MinIO stays sync — wrap it.** The MinIO SDK has no async client. `AuthService.signup()` wraps its upload in `await run_in_threadpool(upload_object, ...)` (Starlette) so it doesn't block the event loop for the duration of the upload.
- **Standalone scripts need a Selector event loop on Windows.** `asyncio.run()`'s default loop on Windows is `ProactorEventLoop`, which psycopg's async driver can't use (`uvicorn` avoids this internally, but a bare script doesn't). `app/scripts/create_admin.py` passes `loop_factory=lambda: asyncio.SelectorEventLoop(selectors.SelectSelector())` to `asyncio.run()` — copy this pattern for any future standalone async script that touches the DB.
- **List endpoints use `fastapi_querybuilder` + `fastapi-pagination`, bypassing the service layer for query construction only.** `QueryBuilder(Model)` (a sync `Select`-builder, no DB access) needs the raw ORM model — that's its integration contract — so these list routes build the query directly against `models.py` instead of going through a service method. But the actual rows never reach the response un-mapped: `apaginate(db, query, transformer=repo.map_many)` (from `fastapi_pagination.ext.sqlalchemy` — NOT the overloaded `paginate()`, whose legacy sync/async auto-detection doesn't suit a genuine `AsyncSession`) funnels every row through the repository's `map_many` → `_to_entity`, so `_to_entity`'s entity-mapping/eager-load guarantees still hold. See any of `positions/tags/company_addresses/job_posts` `router.py` for the pattern; `job_posts`'s list route additionally applies `.options(selectinload(...))` to the `QueryBuilder`-built query before pagination, per the eager-loading rule above. Query params: `?page=&size=` (pagination), `?sort=field:asc,other:desc` (sorting, dot-notation for relationships), `?filters={"field":{"$eq":"value"}}` (JSON filter query — note `$` needs URL-encoding as `%24`).

**API versioning**: all routes are mounted under `/api/v1` via `app/api/v1.py` (e.g. `POST /api/v1/auth/signup`, not `/auth/signup`). `app/api/router.py` is the single aggregator `main.py` imports (`api_router`) — it combines every active version, so `main.py` never changes when a version is added or retired. `/health` is the one deliberate exception — it stays unversioned at the root, matching the convention that infra/monitoring probes shouldn't need to track API versions. If a `v2` is ever needed: add `app/api/v2.py` reusing unchanged domain routers and overriding only what changed, then add one line to `app/api/router.py` to mount it — `main.py` needs no changes.

**Transactions**: repositories only stage changes (`add`/`delete`/query) — they never commit. Any service method that mutates data takes a `UnitOfWork` (via `Depends(get_unit_of_work)`, from `app.core.unit_of_work`) and calls `flush()`/`commit()` on it, not on the repository. `get_user_repository` and `get_unit_of_work` both resolve from the same `Depends(get_db)` session per request, so a service that touches multiple repositories in one operation (e.g. `JobPostService.create()` staging a job post plus its tags/exclusions/templates, or `ApplicationService.create()` staging an application after validating against `JobPostRepository`) can stage all of them and commit once via one shared `UnitOfWork` — keeping that operation atomic. Only put something in `app/core` if more than one domain will need it.

**Entities vs. models — services never see FastAPI or SQLAlchemy types.** Every domain has both a `models.py` (SQLAlchemy, persistence-only) and an `entities.py` (plain `@dataclass`, no ORM, no framework). Repositories are the *only* place that converts between them — `BaseRepository` subclasses implement `_to_entity(orm_obj)`/`_to_model(entity)`; `get_by_id`/`list_all` return entities, `add(entity)` maps to ORM internally and stages it. Services (`AuthService`, `RBACService`) only ever construct/read/pass around entities — they don't import anything from `models.py`, and router endpoints never pass a `UploadFile`/`Request`/etc. into a service (the router extracts plain values first — see `signup()`: the router calls `await resume.read()` and passes `resume_filename`/`resume_content_type`/`resume_bytes`, not the `UploadFile` itself). One consequence: identity generation moved from the ORM to the service — `signup()`/`create_hr_account()` generate `uuid.uuid4()` themselves *before* constructing the entity (needed immediately to build the MinIO resume key), rather than relying on `uow.flush()` to learn a DB-generated id. After `add()` + `commit()`, the service re-fetches via `get_by_id(the_id_it_already_has)` to pick up server-generated fields (`created_at`/`updated_at`) for the response — this is why `UnitOfWork.refresh()` was removed; there's no live, session-attached object left in the service to refresh.

**Exception handling — services raise plain domain exceptions, never `HTTPException`.** `app/core/exceptions.py` defines `DomainError` and five subclasses matching HTTP semantics (`NotFoundError`→404, `ConflictError`→409, `UnauthorizedError`→401, `ForbiddenError`→403, `ValidationError`→400; `DomainError` carries an optional `headers` dict for cases like the `WWW-Authenticate: Bearer` header on an invalid access token). Each domain subclasses these with concrete, named exceptions (`auth.exceptions.EmailAlreadyRegisteredError(ConflictError)`, `rbac.exceptions.PermissionDeniedError(ForbiddenError)`, etc.) and raises them directly — `AuthService`/`RBACService`/`get_current_user`/`require_permission` never construct an `HTTPException` or know their own status code. `app/core/exception_handlers.py`'s `register_exception_handlers(app)` registers one handler per category (mapping to its status) plus the pre-existing catch-all `Exception` → 500 (unhandled bugs/connectivity failures still get logged server-side with a generic body to the client — unchanged). Adding a new domain error: subclass the right category in that domain's `exceptions.py`, raise it — no new handler needed unless the category itself doesn't exist yet.

**Rate limiting**: `app/core/rate_limit.py` exposes `rate_limit(key_prefix, limit, window_seconds)`, a factory returning a FastAPI dependency backed by Redis (fixed-window counter via `INCR`/`EXPIRE`, keyed by `ratelimit:{key_prefix}:{client_ip}`). Apply it via `dependencies=[Depends(rate_limit("signup", limit=5, window_seconds=60))]` on the route decorator (see `auth/router.py`'s `/signup` and `/login`) — not as a handler parameter, since the return value isn't needed. Each endpoint gets its own independent counter (different `key_prefix`), so exhausting `/login`'s limit doesn't affect `/signup`. Exceeding the limit raises `HTTPException(429)` directly — this one deliberately does NOT go through the `app.core.exceptions` domain-error hierarchy, since rate limiting is infra operating right at the HTTP boundary, not a business rule a domain service is deciding. Requires the `redis` container (`docker compose up -d`) and `REDIS_URL` in `.env`.

**RBAC (`app/domains/rbac/`)**: three roles — `admin`, `hr`, `applicant` — seeded via migration, fixed at deploy time (a new role isn't useful until code checks for it). What's actually configurable at runtime is **which permissions each role has**, via the `role_permissions` table:
- `roles` / `permissions` — seeded, effectively read-only in normal operation.
- `role_permissions` (composite PK: role_id + permission_id) — the live, editable part. Managed through admin-only endpoints: `GET /rbac/roles`, `GET /rbac/permissions`, `POST /rbac/roles/{role_name}/permissions/{permission_key}` (grant), `DELETE .../{permission_key}` (revoke).
- Enforcement: `require_permission(permission_key)` (`app/domains/rbac/dependencies.py`) — same factory-returning-a-`Depends()` pattern as `rate_limit`. It checks `role_permissions` **live on every request** — permissions are never cached in the JWT, so granting/revoking one takes effect on the caller's very next request, no re-login needed (verified: revoking `manage_hr_accounts` from `hr` mid-session immediately 403s a still-valid, already-issued HR access token).
- Current permissions: `manage_hr_accounts` (create HR accounts — `POST /auth/hr-accounts`), `manage_rbac` (the `/rbac/*` endpoints themselves), `manage_own_profile` (granted to all three roles), `manage_jobs` (write access across `positions`/`tags`/`company_addresses`/`job_posts`/the 3 assessment template domains — one shared permission, not one per domain), `manage_applications` (review/decide on any application — `GET /applications`, `PATCH /applications/{id}/status`, `PATCH /applications/{id}/extend-assessment-deadline`, `POST /assessment-attempts/{id}/reopen`). Seeded grants: admin → all five; hr → `manage_own_profile` + `manage_jobs` + `manage_applications`; applicant → `manage_own_profile` only. Adding a new gated capability means adding a new `Permission` row (migration) and granting it to whichever roles should have it — either in a migration (default) or live via the grant endpoint.
- `RolePermissionRepository` does **not** extend `BaseRepository` — its table has a composite PK, which doesn't fit `BaseRepository`'s single-`id` `get_by_id` contract. It's the one deliberate exception to "always subclass BaseRepository."
- Dependency direction: `auth` depends on `rbac` (for `require_permission` and role lookup during signup), never the reverse. `auth.dependencies` duplicates a trivial `get_role_repository` factory rather than importing it from `rbac.dependencies`, specifically to avoid a circular import (`rbac.dependencies` imports `get_current_user` from `auth.dependencies`).
- Bootstrapping: nothing in the API can create the first admin (admins are the only ones who create accounts). `uv run python -m app.scripts.create_admin` does it directly via `AsyncSessionLocal()` — reads `ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_FIRST_NAME`/`ADMIN_LAST_NAME`/`ADMIN_CONTACT_NUMBER` from env (prompts for email/password if unset, and falls back to the `DEFAULT_ADMIN_EMAIL`/`DEFAULT_ADMIN_PASSWORD` seed defaults — `admin@example.com` / `admin12345` — if the prompt is left blank; `.env.example` ships these), errors clearly instead of duplicating if that email already exists. See the Windows event-loop note under "Async architecture" above — this script hits it directly since it's not running under uvicorn.
- `User.resume_object_key` is nullable — it's applicant-specific. HR/admin accounts (`create_hr_account`, the seed script) never set it.

**MinIO layout**: resumes are stored under the `applicant_resume/` prefix within the `resumes` bucket (`applicant_resume/{user_id}/{uuid4}_{filename}`, built in `AuthService.signup()`), not directly at the bucket root — keeps the bucket organized if other file types get added later (e.g. HR-uploaded documents would get their own prefix, not dumped alongside resumes).

**Job posting domains (`positions/`, `tags/`, `company_addresses/`, `job_posts/`)**: four separate domains, not one bundled domain — `Position`, `Tag`, and `CompanyAddress` are independent, fully-CRUD'd reference resources with zero knowledge of each other or of `JobPost`; `JobPost` is the only one that depends on the other three (one-way, same direction as `auth` → `rbac` — never the reverse). Splitting them was a deliberate correction: they were originally one `jobs` domain (mirroring `rbac`'s multi-model shape), but unlike `Role`+`Permission`+`RolePermission` — which only make sense together — these three have no shared business concept, so bundling them violated single-responsibility at the domain level, not just the class level. Design notes:
- **Public read, gated write.** Every `GET` on `/company-addresses`, `/positions`, `/tags`, `/job-posts` is unauthenticated (job posts are a public listing). Every `POST`/`PUT`/`DELETE` across all four requires the `manage_jobs` permission (seeded, granted to `admin`+`hr` by default — same shape as `manage_hr_accounts`). One shared permission across four domains is intentional — no need for `manage_positions`/`manage_tags`/etc. unless finer-grained control is actually requested.
- **`job_post_exclusions` models the relationship only.** A job post can list other job posts it excludes (`excluded_job_post_ids`) — intent: "don't let applicants of job post A apply to job post B." Enforced by the `applications` domain at apply time.
- **`JobPostCreate` supports inline template selection.** `pre_assessment_template_id`/`culture_fit_template_id`/`technical_assessment_template_id` are optional fields on create, validated and attached in the same transaction as the job post insert — same inline-at-create pattern as `tag_ids`/`excluded_job_post_ids`. Changing a template after creation still goes through the dedicated `POST/DELETE /job-posts/{id}/{type}-templates/{template_id}` endpoints (same asymmetry as tags: inline at create, dedicated endpoints for later changes). See `docs/plans/assessments-domain.md` for the full template/assessment design.
- **Cascade rules are deliberately asymmetric.** Deleting a `JobPost` cascades its own `job_post_tags`/`job_post_exclusions` rows (both sides — as excluder and as excluded) since those rows are owned by the job post. Deleting a `Position`/`CompanyAddress`/`Tag` that's still referenced by a job post does **not** cascade — it hits a live FK, which each domain's own service catches (`IntegrityError` → `uow.rollback()` → its own `*InUseError`, a `ConflictError` → 409) rather than letting it surface as a raw 500.
- **`BaseRepository.update(entity)` is repo-specific, not generic.** `add(entity)` maps a *new* entity to a transient ORM object and stages an INSERT — reusing it for an update would attempt a duplicate-PK insert. Each of the 4 repositories implements its own `update(entity)`: fetch the existing session-attached ORM row by id, mutate its columns from the entity, and let SQLAlchemy's unit-of-work detect the diff and emit the UPDATE on commit. `BaseRepository` doesn't provide this generically because not every entity's PK attribute is named `.id` (e.g. `RevokedRefreshToken` uses `.jti`).
- **`JobPostService.create()` flushes before staging tag/exclusion rows.** `job_post_tags`/`job_post_exclusions` reference `job_posts.id` by a plain FK column, not a SQLAlchemy `relationship()`, so the session's automatic insert-ordering can't infer that the `JobPost` row must exist first. An explicit `uow.flush()` after `job_posts.add(...)` (and before `add_tag`/`add_exclusion`) forces that ordering within the same still-uncommitted transaction.
- `employment_type`/`status` are `StrEnum`s (`app/domains/job_posts/enums.py`) — a bad value gets rejected by Pydantic at the request boundary (422) before the service ever runs, same principle as the `EmailStr` fix on signup. No `InvalidEmploymentTypeError`-style domain exception exists because there's nothing left for the service layer to validate.

**Applications (`app/domains/applications/`)**: an applicant's candidacy against one job post. `POST /applications` is applicant-only (`OnlyApplicantsCanApplyError` if an HR/admin token calls it), requires the job post to be `published`, and enforces exclusions: if the job post lists another job post as excluded and the current user has *any* application against that excluded post, the request 403s (`ApplicantExcludedError`) naming the conflicting job post by title, not just its id. A partial unique index (`ux_applications_active_per_job_post`, `WHERE status != 'withdrawn'`) enforces one *active* application per applicant per job post at the DB level — `ApplicationService.create()` relies on catching the resulting `IntegrityError` (→ `DuplicateApplicationError`, 409) rather than a pre-check, since withdrawing and re-applying is allowed but a live duplicate isn't. `resume_object_key` is copied onto the `Application` row at apply time — a deliberate snapshot, not a live reference to `User.resume_object_key`, since the applicant could update their resume later without that silently changing what a job post reviewer already saw.
- **Status pipeline** (`ApplicationStatus`, 8 values): `applied → prescreening → interview → {success, failed}`, with `denied` reachable from `applied` or `prescreening`, plus two side-channel terminal states reachable only through their own dedicated action, never through `PATCH /applications/{id}/status`: `withdrawn` (applicant-only, via `POST /applications/{id}/withdraw`, only from `applied`/`prescreening`/`interview`) and `disqualified` (system-only, via the scheduled sweep below). **`enums.py` owns the transition graph** — `ALLOWED_TRANSITIONS` (the forward moves `PATCH /applications/{id}/status` accepts; else `InvalidApplicationStatusTransitionError`, 400) and `WITHDRAWABLE_STATUSES`, both moved out of `service.py` so the schema layer can read them too. `ApplicationOut` **and** `ApplicationReviewOut` carry `allowed_status_transitions: list[str]` + `can_withdraw: bool` (a `_StatusCapabilitiesMixin` `model_validator` fills them from `status`), so the frontend never re-encodes the pipeline rules.
- **Ownership check returns 404, not 403.** `ApplicationService.get()` allows the owning applicant or anyone with `manage_applications`; anyone else gets `ApplicationNotFoundError` (404) rather than a 403, so the endpoint doesn't leak that a given application id exists to someone who shouldn't see it. `GET /applications/{id}/resume` (streams the MinIO object, `Content-Disposition: attachment`) reuses that exact check — `ApplicationService.get_resume()` calls `get()` first, then `run_in_threadpool(storage.get_object, ...)` (MinIO SDK is sync, same as the upload); a missing object → `ResumeUnavailableError` (404).
- **List endpoints are projection queries, not entity hydration**, same pattern as job posts' paginated list but router-facing instead of `QueryBuilder`-based (filtering here is a couple of explicit typed query params — `job_post_id`, `status`; `list_for_applicant` also takes an optional `job_post_id` for the careers "have I already applied here" check — not the generic JSON filter syntax): `ApplicationRepository.list_for_review()` joins in `job_posts`/`users` for a curated HR-facing column set (job title, applicant name/email), `list_for_applicant()` joins in just `job_posts` for the title. Both return a raw `Select`, paginated via `apaginate(db, query, transformer=lambda rows: [...])` in the router. `ApplicationService.list_for_review()`/`list_for_applicant()` are thin pass-throughs that exist solely so the router depends only on the service, never the repository directly — there's no business logic to add on top, this is purely a layering boundary.
- **`GET /applications/stats`** (manage_applications, optional `?job_post_id=`) and **`GET /job-posts/stats`** (manage_jobs) — each one `SELECT status, count(*) … GROUP BY status` in the repository, zero-filled to every enum value in the service, returned as `{ by_status, total }`. For the ATS dashboard, replacing N one-row list calls + client-side summation. Both `/stats` routes are declared **before** their `/{id}` route so `stats` isn't parsed as an id.
- **Assessment deadline + extensions.** `assessment_deadline` is set at apply time (`now + job_post.assessment_window_days`, default 4). `PATCH /applications/{id}/extend-assessment-deadline` (manage_applications-gated) accepts either an absolute `new_deadline` or a relative `extend_by_days` (added to the *current* deadline, not `now`) and writes an append-only `AssessmentDeadlineExtension` row (`reason` required) — never edited or deleted, surfaced via `GET /applications/{id}/assessments`. Extending the deadline on a `disqualified` application is also the **only** way to un-disqualify it (`ApplicationService.extend_assessment_deadline()` flips the status back to `applied` as a side effect) — there's no separate "revive" endpoint, since nothing else can move an application out of that terminal status.
- **Router-level composition, not a service dependency.** `POST /applications` calls both `ApplicationService.create()` and `AssessmentService.create_attempts_for_application()` — `applications/router.py` is the one place that constructs both services together. Neither service imports the other's module: `assessments` depends one-way on `applications` (an attempt belongs to an application), so `applications` depending back would be a cycle. The same composition-root pattern is used by the two scheduler scripts below.

**Assessments (`app/domains/assessments/` — see the directory-grouping note above and `docs/plans/assessments-domain.md` for the full history)**: before an application can reach human `prescreening` review, the applicant must complete up to 3 tests — pre-assessment, culture-fit, technical — whichever templates the job post has attached (0–3; none are mandatory). `POST /applications` creates one `AssessmentAttempt` per attached template via `AssessmentService.create_attempts_for_application()`.
- **Three nested timing layers.** (1) `applications.assessment_deadline` — days, covers all attempts on one application, extendable (see above). (2) Template-level `time_limit_minutes` — the whole attempt's timer, starts on `started_at` (set the first time any question is opened), checked lazily on the next `start_question`/`submit_answer` call (`AssessmentService._check_and_apply_layer2_expiry`) rather than by a background job. (3) Per-question `time_limit_seconds` (nullable) — mainly used by culture-fit templates; a question past its own timer is **silently skipped**, not rejected (`_compute_current_question` just moves to the next one).
- **Strictly sequential, one question at a time.** `_compute_current_question()` walks the template's questions in `order_index` order and returns the first one that's still open (no live answer yet, or answered but its own timer hasn't lapsed) — `start_question`/`submit_answer` both 400 (`NotCurrentQuestionError`) if the caller names any question other than the current one. This exists specifically so an applicant can't game the shared attempt-level timer by working ahead on an easy question while a hard one's per-question clock is still running unseen.
- **`GET /assessment-attempts/{id}` (owner-only) is the applicant's read path for *taking* an attempt** — `AssessmentService.get_attempt_detail()` returns the attempt status/timers plus **only the current question** (never the full list — same anti-work-ahead reason as above) and `answered_count`/`total_questions`. It's pure: unlike `start_question`/`submit_answer` it never applies layer-2 expiry. Added because the 3 template `GET` endpoints are `manage_jobs`-gated, so an applicant otherwise has no way to discover the current question's id or its prompt/type/config. `_require_owned_attempt` gates it (applicant who owns the parent application only; HR sees attempts via `GET /applications/{id}/assessments`).
- **`AssessmentAttemptOut` carries `answered_count` + `total_questions`** everywhere it's returned (the `/applications/{id}/assessments` list, and the `submit_answer` / `reopen` responses). `answered_count` is a `model_validator` over the schema's own `answers`; `total_questions` needs the template, so `AssessmentService._with_total_questions()` sets it on the entity in `list_for_application()` and both mutation return paths (the raw repo entity — scheduler paths — leaves it 0). Saves the frontend recomputing progress and needing a gated template fetch for the denominator.
- **Polymorphic dispatch via `template_type`, not a DB foreign key.** `AssessmentAttempt.template_id` (and `AssessmentAnswer.question_id`) carry no FK — they can point into any of 3 independent tables depending on `template_type`/the parent attempt's `template_type`, and Postgres has no "FK to one of several tables." `AssessmentService._get_template()` dispatches to the right one of `self._template_repos: dict[TemplateType, Repo]` (keyed by the private `TemplateType` enum: `pre_assessment`/`culture_fit`/`technical`) at the application layer instead. This is the one real cost of the 3-independent-domains split, called out deliberately rather than hidden.
- **Reopen is soft-invalidation, not deletion — and both reopens and deadline extensions are append-only audit logs.** HR reopening an `expired` attempt (`POST /assessment-attempts/{id}/reopen`, manage_applications-gated, `reason` required) sets `superseded_at` on the attempt's live answers rather than deleting them (a partial unique index enforces "one live answer per question" with `WHERE superseded_at IS NULL`), resets the attempt to `not_started`, and writes an `AssessmentAttemptReopen` row — mirroring `AssessmentDeadlineExtension`'s shape exactly, both surfaced together via `GET /applications/{id}/assessments`. Reopening is blocked if the parent application is already `disqualified` (extend the deadline first — see above).
- **The disqualification/expiry sweep runs as two composition-root scripts, not service methods.** `app/scripts/expire_overdue_assessment_attempts.py` (layer 2: `AssessmentAttempt`s past their template's `time_limit_minutes`) and `app/scripts/disqualify_overdue_applications.py` (layer 1: `Application`s past `assessment_deadline` that aren't fully assessed) are each independently runnable (`uv run python -m app.scripts...`) and are the only places that construct `AssessmentService` and `ApplicationService` together, for the same one-way-dependency reason as the `POST /applications` router endpoint above. `app/core/scheduler.py` wraps both in an APScheduler `AsyncIOScheduler` on a 15-minute interval, wired into `main.py`'s `lifespan` — order matters (`expire` before `disqualify` in the same tick, so a just-expired attempt is visible to the same run's disqualify check). **This file is the only thing deleted when the cron responsibility moves to Airflow** — the two scripts map 1:1 onto two future Airflow tasks (`expire_attempts_task >> disqualify_applications_task`) and contain the actual business logic; `scheduler.py` itself is a zero-logic timer wrapper, by design, for that migration.
- **Shared question-type vocabulary lives in `app/core/question_types.py`**, not any one domain — `QuestionType` (8 values: text, long_text, single_choice, multiple_choice, boolean, number, rating, date), `validate_question_config()` (shape-checks what HR authors — `single_choice`/`multiple_choice` need a non-empty `options` list; `multiple_choice` `min_selections`/`max_selections` must be non-negative ints with `min <= max <= len(options)`; `text`/`long_text` `max_length` non-negative; `number`/`rating` `min < max`; `date` `min_date`/`max_date` valid ISO with `min <= max`), and `validate_answer_value()` (checks what an applicant submits against the question's type/config). It's in `app/core` because 4 domains need it — the 3 template domains (validating authored questions) and `attempts` (validating submitted answers) — and none of them may depend on each other for it.
- **Job-post-to-template attachment** is 3 real-FK join tables (`job_post_pre_assessment_templates`, etc.) each with `job_post_id` as the *sole* primary key (not composite with `template_id`) — structurally enforcing "at most one template of this type per job post" instead of a separate `UniqueConstraint`. See "`JobPostCreate` supports inline template selection" above for how HR attaches these.

## Testing

`tests/unit/` mirrors `app/`'s structure (`core/`, `auth/`, `rbac/`, `applications/`, `assessments/{attempts,pre_assessment_templates,culture_fit_templates,technical_assessment_templates}/` — note the nesting under `assessments/` mirrors `app/domains/assessments/`'s own grouping). Run with `uv run pytest` (or `uv run pytest -v`) — **no Docker containers required**; these are pure unit tests exercising services directly with `unittest.mock.AsyncMock` repositories, which is the whole point of the entities/domain-exceptions split above (verified by running the full suite with Postgres/MinIO/Redis all stopped — 106 pass as of the assessments/applications build-out). `asyncio_mode = "auto"` is set in `pyproject.toml`, so `async def test_...` functions run without a `@pytest.mark.asyncio` decorator.

- `test_service.py` per domain — constructs the domain's service class with `AsyncMock()` repositories (not `MagicMock()` — the services `await` every repository/`UnitOfWork` call now, and a plain `MagicMock` return value isn't awaitable), asserts on raised domain exceptions and on what the mocks were called with (e.g. `role_permissions.grant.assert_called_once_with(role.id, permission.id)`). No real database. `test_exception_handlers.py`'s throwaway routes are untouched — they're sync, isolated, and unrelated to the app's real DB-backed routers.
- `tests/unit/assessments/attempts/test_service.py`'s `make_service()` returns an 8-tuple including all 3 mocked template repositories (constructing `AssessmentService` needs all 3, per its constructor signature above), even though most test cases only exercise one — `make_attempt()` defaults to `template_type=TemplateType.TECHNICAL` unless overridden.
- `test_security.py` — pure roundtrip tests for `hash_password`/`verify_password`/`create_access_token`/`create_refresh_token`/`decode_token`.
- `test_question_types.py` (`tests/unit/core/`) — the `validate_question_config`/`validate_answer_value` shape-validation tests, one level removed from any single domain since the module they test lives in `app/core`.
- `test_exception_handlers.py` — a throwaway `FastAPI()` app + `TestClient` proving each `DomainError` category maps to its documented status code (and that `UnauthorizedError`'s `headers` argument actually reaches the response).
- When a fake repository needs to simulate "after commit, the DB filled in server-generated columns" (e.g. `created_at`), don't return the same entity object that was passed to `add()` — timestamps on it are still `None`. Use `dataclasses.replace(entity, created_at=..., updated_at=...)` to simulate what a real `get_by_id` re-fetch would return (see `_as_persisted` in `tests/unit/auth/test_service.py`) — this bit two tests during development, it's not an application bug.

No integration tests yet (nothing hits a real Postgres/MinIO/Redis), and no unit tests at all yet for `job_posts` or `positions`/`tags`/`company_addresses` — these domains have real logic living in the repository layer itself (the tag/exclusion join queries, the cascade-vs-restrict delete behavior, the template-attachment join tables) that mocked-repository unit tests structurally cannot exercise. Worth adding before these domains grow further.

## Environment

- Package manager: `uv` (see `uv.lock`). Use `uv add <package>` to add dependencies, `uv run <script>` to run things — don't call `pip` directly.
- Python version is pinned via `.python-version` (3.14).
- Copy `.env.example` to `.env` before running anything — `app/core/config.py` (pydantic-settings) requires `DATABASE_URL`, `JWT_SECRET_KEY`, and `MINIO_*` vars to be set.
- Infra (Postgres + MinIO) runs via Docker: `docker compose up -d`. `docker-compose.yml` matches the defaults in `.env.example` (do not change one without the other).
- Migrations: `uv run alembic revision --autogenerate -m "..."` then `uv run alembic upgrade head`. `alembic/env.py` is wired to `app.core.database.Base` — new domain models must be imported there (see the `from app.domains.auth import models` line) or autogenerate won't see them. Generated files under `alembic/versions/` are excluded from ruff (`extend-exclude` in `pyproject.toml`) — don't hand-edit them for style.
- Run the API: `PYTHONUTF8=1 uv run fastapi dev app/main.py`. The `PYTHONUTF8=1` is required on Windows — without it, `fastapi dev`'s startup banner crashes with a `UnicodeEncodeError` trying to print an emoji through the cp1252 console codec.
- Auth design: access + refresh JWTs (see `app/core/security.py`), passwords hashed with `bcrypt` directly (not `passlib`). No email verification yet.
- Refresh-token revocation: every JWT carries a `jti`. `POST /api/v1/auth/logout` records the refresh token's `jti` + expiry in the `revoked_refresh_tokens` table (`app/domains/auth/models.py`); `POST /api/v1/auth/refresh` rejects any token whose `jti` is in that table. Access tokens are NOT revocable (they just expire — 30 min default) — only refresh tokens are checked against the denylist. There's no cleanup job for expired rows in that table yet.
